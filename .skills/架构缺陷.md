## 已关闭（按域摘要）

下列机制均已修复，且均有对应门禁或 verify 默认判据；细节与提交哈希见 git 历史，此处只保留**可检索的机制名**。

### 分层与模块边界

- **apl 不得直连 hal**：时钟与 `HAL_Init` 收入 `board_system_init()`，`LAYER_DEPENDENCIES["apl"]` 含 `bsl`；`layer-deps`。
- **fml 收紧为 `bsl + osl`**，禁止偷 include hal；`layer-deps` 第三段。
- **尖括号 include 本仓层头可绕过判定** → 要求改成引号形式；`layer-deps` 第四段。
- **`extern` 声明建立层边但不被 include 扫描** → 符号前缀判定；`layer-deps` 第五段。
- **层头归属误含 `tool/` 下第三方头** → 判定域改为 `STATIC_LIB_DIRS`。
- **FreeRTOS 配置关而 `timers.c` 仍编译** → `config_gated_sources` + `freertos-unit`。
- **fml_panic 归属在 LED 模块** → 独立 `fml_panic.c` + `collect_panic_entry_ownership_errors`；`panic-code`。
- **层头里的条件声明依赖宏顺序**：`bsl/inc/bsl_i2c_gpio.h` 按 `BOARD_DTS_BEEP_VIA_PCF8574` 声明 `bsl_board_i2c_gpio_bus()/ready()`，而该宏由 `board_dts.h` 提供；`bsl/src/bsl_i2c_gpio.c` 原先把自身头排第一 ⇒ 解析时宏未定义、声明整段被跳过，定义处没有原型（GCC `-Wmissing-prototypes`；编译仍过是因为 C 允许无原型定义）。修法：`board_dts.h` 先 include，并删掉 `#if` 块内重复的同名 include。
- **同一个设备驱动对象两处声明**：`bsl/inc/bsl_i2c_gpio.h` 里手写的 `extern const struct bsl_device_driver bsl_driver_brd_i2c_gpio;` 与生成的 `bsl/inc/board_device_registry.h` 重复（`-Wredundant-decls`）。以生成头为唯一来源，手写声明删除。
- **设备 api 结构里带着一个从不被调用的 `init`**：`bsl_device_api.h` 的四类 `*_api_t`（debug_uart / leds / keys / beep）各有 `void (*init)(void)`，与 `bsl_device_driver_t.init` 指向同一个函数；全仓唯一的初始化入口是 `bsl_init.c` 的 `dev->driver->init()`，`fml` 三个消费点只用 `set/on/off/toggle/pressed/pin_high/puts`，从不碰 `api->init`。这和「DTS 极性写两遍」是同型陷阱——改 api 里的 `.init` 会静默不生效，而两处恰好同名同签名，肉眼难辨。`-Wredundant-decls` 抓不到（不是重复声明）、`-Wmissing-prototypes` 也抓不到（签名正确且有原型）。已删 4 个成员，`.rodata` 省 16 B（实测 user `text` 14420→14404、userdebug 16500→16484，两档同步 -16 B，恰为 4×4 B 函数指针）。
- **设备初始化失败在卡上不可见**：`bsl_device_driver_t.init` 曾是 `void (*)(void)`，没有返回通道。`board_beep` 在 I2C 总线没起来时，`pcf8574_write()` 返回的 `BSL_ERR_IO` 被 `beep_apply_shadow()` 丢弃，设备照样被记成"已初始化"，之后每次 `set` 静默无效（现场只表现为"蜂鸣器坏了"）；`board_debug_uart_init` 同样把 `HAL_UART_Init` 的返回值 `(void)` 丢掉。现已改为 `bsl_err_t (*init)(void)`，`bsl_device.c` 里另起 `static uint8_t s_state[]`（bss 实测 6 B，`s_devices` 是 const 不能加字段），新增 `bsl_device_is_ready()` / `bsl_device_state()` / `bsl_device_mark()`；失败写状态位 + 一条 ERR，且**打印前先判 `bsl_device_is_ready(BSL_DEV_DEBUG_UART)`**——debug_uart 自己失败时写 UART，会把 `Instance=NULL` 的 huart 交给 `HAL_UART_Transmit`，初始化失败反而变成 HardFault。守门：`bsp` 组第三段（把失败分支的 `FAILED` 改成 `READY` → 期望 `mark FAILED` 报红，实测 294.5 s PASS）。
- **驱动 API 的类型擦除（`bsl_device_driver_t.api` 是 `const void *`）**：`fml_led.c` 与 `fml_button.c`（两处）各自把 `dev->driver->api` 强转成自己的 `*_api_t`，结构类型在编译期丢失——把 leds 的 api 挂到 keys 的 driver 上编译全绿，运行期按错布局取函数指针。Zephyr 用 `DEVICE_API` 让 api 类型参与编译期检查，这是本工程与它最实质的一处差距。**已落地（4.1「驱动 API 类型化」）**：binding 新增 `api_type` / `api_sym`（leds / keys / pcf8574-beep 三份声明；只写一条时生成器抛 `ValueError`），生成器产出 `static inline const <api_type> *bsl_devapi_<node>()`（`board_device_registry.h`），fml 三处改为直接调用；`bsl_device_driver_t` 只剩 `init`。顺带删掉零消费的 `bsl_debug_uart_api_t` / `bsl_api_debug_uart`（`puts` 全仓无人用，`bsl_log` 直连 `board_debug_uart_puts`）。实测 user `text` 14716→**14560**（-156 B）、userdebug 16736→**16644**（-92 B），RAM 18544 不变。守门：新增 `collect_device_api_errors()`（5 条：driver 不得再有 `api` 成员、fml/apl 不得出现 `(const bsl_*_api_t *)`、生成物必须有三个访问器、三处消费点必须调用、debug_uart api 不得回来），`bsp` 组第四段（把 `const void *api` 塞回 driver 结构 → 判据报红；整组 4 段实测 241.7 s PASS，`--assert-map` 实测固化 4 条断言）。

- **VOSRDY 裸等**；`startup-guard`。
- **`HAL_Init` 返回值丢弃**；`boot-init`。

- **`osl_hal_tick_ms_from_dwt` 外部链接但只在本 TU 用**：`HAL_GetTick` 与首拍对齐都调它，别的 TU 从不引用，却占着一个全局符号（`-Wmissing-prototypes`）。改 `static`；`tick-source` 的判据本来就有 `udiv` 兜底，`-Os` 内联后仍 PASS。
- **`key_hw[]` 手写 4 条初始化器、数组长度却取生成值 `BOARD_DTS_KEY_COUNT`**：键数"变少"只是编译错误（too many initializers），"变多"则第 5 项起被零初始化（`port=NULL`）→ `board_key_init` 遍历到它 → `bsl_gpio_init_input(NULL, …)` 一路静默 → `HAL_GPIO_Init(NULL, &gpio)` 写 `GPIOx->MODER` → 空指针 HardFault（码 6）。生成器现在产出 `BOARD_DTS_KEY_HW_INITIALIZERS`（与 `BOARD_DTS_LED_PINS_INITIALIZER` 同形），`board_key.c` 写成 `key_hw[] = { BOARD_DTS_KEY_HW_INITIALIZERS }` 并加尺寸 `_Static_assert`。守门：`board-key` 两段破坏（换回手写形态 / 删掉尺寸断言）＋ 第三、四段守着极性真源（详见下条）。
- **`board_panic_beep_silence` 的 PCF8574 分支硬编码 `|= BIT`**：与同文件 GPIO 分支（按 `BOARD_DTS_BEEP_ACTIVE_HIGH` 算 BSRR）语义相反。当前 `BEEP_ACTIVE_HIGH=0` 下"置 1"恰好等于静音，改成 active-high 的蜂鸣器后，panic 播报的静音步骤反而会**拉响**它（且发生在关中断后的播报路径上）。改为调 `beep_set_pcf8574_logical(0)`（与 `board_beep_init` 同一路径），极性判断只剩一处。
- **`bsl_device_at/get/count` 把枚举数当数组长度**：`s_devices[]` 的条数由 `BOARD_DEVICE_REGISTRY_APPLY` 展开决定，三个访问函数却拿 `BSL_DEV_COUNT` 做边界与下标。当前 6 条恰等于枚举数、顺序也一致，所以"恰好安全"；一旦某设备在 DTS/registry 里没有条目（生成器少发一条 `M(...)`），`bsl_device_at(BSL_DEV_COUNT-1)` 会取到数组外内存，`bsl_init_run()` 随即读它的 `init_level` / `driver` 并调用 —— 启动期随机跳飞，无任何编译期或运行期提示。**修法**：条数改用 `sizeof(s_devices)/sizeof(s_devices[0])`，`bsl_device_get` 改成按 `.id` 线性查找（线性遍历，不依赖"下标 == 枚举值"），不再依赖"下标 == 枚举值"这个隐式契约；再加一条 `_Static_assert`，把"注册表 `M(...)` 条数 == `BSL_DEV_COUNT`"抬成编译期契约 —— 运行期判 NULL 只是兜底，少了设备时不该只是静默缺功能。守门：`bsp` 组第二段（手改生成物删掉一条 `M(...)` 后必须编译失败）。
- **DTS 里按键极性写了两遍，只有一份生效**：`apollo.dts` 的每个 key 节点同时写 `gpios`（第三 cell 是 GPIO flag，1 = `active_low`）和 `pressed-low/high`，而 `parse_board_dts` 在 `if "gpios" in inner:` 分支里只走 `_parse_gpios_block`，`pressed-*` 整段不读。后果是"把 `pressed-low` 改成 `pressed-high` 什么也不会发生"——本轮造极性破坏态时实测踩到：`update` 照样 EXIT=0、生成物一个字节未变，门禁段假绿。**修法**：生成器对"同时写了 `gpios` 与 `pressed-*` 且极性矛盾"的节点直接抛 `ValueError`。守门：`board-key` 第三段（改 flags + `pressed-*` 同步改 → 期望表报红）、第四段（只改 `pressed-*` → 报「两者矛盾」）。
- **`bsl_device_find_by_compat` / `compat_id` / `BSL_COMPAT_*` 是一套零消费的面子 API**：绑定已经在生成期完成（binding YAML → `board_device_registry.h` 的 `M(...)` 静态表），运行期没有"按 compatible 查设备"的需求 —— `bsl_device_find_by_compat()` 全仓零调用，`bsl_device_t.compat_id` 的唯一读点就在该函数自身（"字段只被一个没人调的函数读"）。留着的实际风险是误导：后来者会以为查找走 compat，去改 `BSL_COMPAT_*` 枚举，改完什么也不发生。**已删**：函数 + 字段 + 生成器里的 `compat_enums` 段 + 6 份 binding 的 `compat_id:` 行（早前报告写"7 份"是笔误，实测 6 份），`M(...)` 由 5 参收成 4 参。实测 `s_devices` = **96 B**（6 × 16 B，每行 id/name/level/driver 四字段；删前每行 20 B），`find_by_compat` 不在符号表；`build/checks/dts.py` 的 `_EXPECT_REGISTRY` 同期从 4 元组收成 3 元组，`bsp` 组第二段的 `M(...)` 锚点跟着改。守"删干净"的是 `device-dts` 组（注册表逐条对拍）。

### 2) `bsl_fdt_prop_flag` 只判存在、不看值（P1·已修）

**机制**：原实现 `return fdt_find_prop(node, name, &len) != NULL;` —— 只回答"有没有这个属性"，
第四 cell 的值被丢弃。而 DTS 里 `active-low = <0>` 是合法写法（显式声明高有效），
`pressed-high = <0>` 同理；于是**只要属性出现就当 1**，LED / KEY 极性整体反相。
DTB 里 0 与 1 语义相反，固件全当 1 —— 属于无任何告警的静默错。

**改后**：不存在 → 0；`len == 0`（布尔属性 `active-low;`，出现即真）→ 1；
`len != 4` → 0（不猜长度）；`len == 4` → `fdt_be32(val) != 0U`。
调用点 2 处：`board_rt.c` 的 `leds` 子节点（:142 附近）与 `keys` 的 `pressed-high`（:200 附近）。

**代价**：`bsl_fdt_prop_flag` 20 B → 52 B（`nm -S`：`0x14` → `0x34`），text **+32 B**
（86088 → 86120；user 83232 → 83264）。`.dtb` 段随代码段前移整体 +0x20：
`_sdtb 0x080056d0` → `0x080056f0`，`_edtb 0x08015060` → `0x08015080`，跨度 63888 B 不变。

### 3) `HAL_UART_MspInit` 非本实例静默返回（P1·已修）

**机制**：`board_debug_uart.c` 的 Msp 回调开头
`if (s_instance == NULL || huart->Instance != s_instance) { return; }`。
HAL 在**每次** `HAL_UART_Init` 都调这个全局弱回调；第二路 UART（或任何非 debug 口）走到这里
既不配引脚也不配 NVIC，而 `HAL_UART_Init` 仍返回 `HAL_OK` —— 串口"初始化成功但没波形"，
现场只能靠示波器才发现。回调是对外可见的弱符号，静默忽略等于把错误藏起来。

**改后**：非本实例时置 `s_pinmux_failed = 1U` 再返回，由 `board_debug_uart_init()` 的返回值暴露
（该返回值已有调用点检查）。原则：宁可报错，也不假装成功。

### 4) `_sync_out_dir_exports`：隐式跨模块写全局（已删）

**机制**：`generate.py` 用这个函数遍历 `sys.modules`，把 `OUT_*` 重新写回**每个**模块的命名空间；
`build.py` 的 5 处 `OUT_RELEASE_DIR` / `OUT_ARTIFACT_DIR` 靠它才能与 `generate.py` 里的赋值同步。

**改后**：`build.py` 一律 `generate.OUT_ARTIFACT_DIR` / `generate.OUT_RELEASE_DIR` 属性访问（6 处替换），

## 2026-11-22 第四轮：死数据与死 API

### 1) DTB 的 `hse-frequency` 无人消费（P1·已修）

**机制**：`out/dts/apollo.dts:13` 的 `/clocks` 节点声明 `hse-frequency = <25000000>`，
`board_rt.c` 的 `parse_clocks()` 把它解析进 `s_rt.hse_hz`，而 `board_rt_hse_hz()` **全工程零调用**
（全仓 grep 与 `nm` 都只有「声明 + 定义」两行）。于是"板级时钟事实住在 DTB"只是看起来成立：
PLL 实际读的是编译期 `HSE_VALUE`（`hal/periph/inc/stm32f4xx_hal_conf.h:96`），
DTB 里那份写错、或换板时只改了一处，不会有任何反应。这与第三轮修的 `prop_flag` 同型 ——
**解析了却没人问结果**，比没解析更危险，因为它给人一种"已经校验过"的错觉。

**改后**：`board_system_init()` 在 `SystemClock_Config()` 之前对拍
`board_rt_hse_hz()` 与 `HSE_VALUE`：`0` = DTB 未声明（不约束，编译期宏仍是唯一事实），
非 0 且不等 → **返回 3**。`parse_clocks()` 不再 `(void)` 吞返回值 —— 属性缺失或长度不对时
显式回落 0（"未声明"），不再让"读失败"和"没写"混成同一个静默状态。

**证据**：`board_system.c` 四个返回点 `1 / 3 / 2 / 0`；`nm` 里 `board_rt_hse_hz` 从零调用变为有引用；
两档 build EXIT=0、零真告警；text 86120 → **86168（+48 B）**，user 83264 → **83296（+32 B）**。
故障码 3 同步进 `board_system.h`、`系统设计.md`、`用户指南.md`、`搭建环境.md`、`test_case.md`（5 处）。

### 3) 四个零调用的公开 API（P2·已删）

| 符号 | 原实现 | 判定 |
|---|---|---|

**证据**：`nm` 里 4 个符号全部消失，两档 EXIT=0。

**判定口径（重要）**：`board_led_*` / `board_key_*` / `board_beep_*` 在 `name(` 文本计数里也只有 1，

### 4) `parse_i2c` / `parse_uart` 边校验边写全局（P2·已修）

**机制**：`board_rt.c` 的 leds / keys 段落注释写着"全程解析到局部变量，全部成功才提交 `s_rt`"，
但 `parse_i2c` 与 `parse_uart` 没有照这个范式做：

| 函数 | 半套状态 |
|---|---|
| `parse_i2c` | 先把 `s_rt.scl_port` / `s_rt.sda_port` 写进去，再判 NULL / pin>15；任一步失败就 return，留下「端口已设、pin 仍 0、`i2c_ok` 仍 0」 |
| `parse_uart` | 先把 `s_rt.tx_port` / `s_rt.rx_port` 写进去，再判 `baud == 0`；失败时留下「端口字符已设、其余仍 0」 |

`i2c_ok` / `uart_ok` 能把**按 ready 判**的消费者挡住，但 `board_rt_i2c_scl_port()` /
`board_rt_uart()` 的其它字段会老实返回那个"设了一半"的值 —— 不看 ready 的调用方就拿到错脚。同一文件里两种范式，
下次谁再照着其中一个写就是三份不一致。

**改后**：两个函数都改成「局部变量 + 全部校验过再一次提交」，与 leds 完全同构；注释写明为什么。

**证据**：两档 build EXIT=0、零真告警、text 不变（86168）—— 只是把赋值挪到 if 之后，编译器生成的代码量相同。

### 2) `.dtb` 段"按 4 字节对齐后一致"是错的（P2·已修）

我第一版 `refcheck` 就是用 4 B 对齐去对拍段跨度，首跑直接报"不一致"——**判据本身错了**，
不是产物错。文档（`系统设计.md` 的段描述）与 `.s` 注释也都没写清 16 B 的来由。

**改后**：判据改用内容边界符号（`bsl_dtb_start` / `bsl_dtb_end`）逐字节等长；段跨度只作附注并打印
填充量；文档改成"跨度 = 内容 + 13 B 填充"；`.s` 两处 `.align 4` 都加注释写明 2^N 语义与对拍该用哪组符号。

### 1) `bsl_log` 的环形缓冲没有互斥（P1·已修）

**机制**：`bsl_log.c` 的 `s_ring[8][40]` / `s_line[40]` / `s_head` / `s_line_len` 是 bsl 内部的 static。
上电后有两个任务会写它——`apl/src/app_sample.c` 起的 `led_blink` 与 `button`（各自周期里都打一行日志），
而 `bsl_log_puts()` 全程没有任何保护，每条语句之间都可能被任务切换打断：

| 交错点 | 后果 |
|---|---|
| A 已 `ring_absorb(s)` 把半行写进 `s_line`，被 B 抢占并写完自己一行 | A 恢复后继续往**已被 B 提交并清零**的 `s_line` 里写，把 B 那行的残尾当成自己的前缀 |
| A 与 B 同时执行 `s_head = (s_head + 1) % N` 的读-改-写 | 两行只前进一格，最早的一槽内容被覆盖后**直接消失** |
| 两者同时 `board_debug_uart_puts()` | `HAL_UART_Transmit` 非重入，两条字符串的字节在 TX 上逐字节交错 |

第一种最恶劣：现场读到的是一行"两条日志拼起来"的文本——比丢一行更误导，排查会从错误的模块开始。
第六轮把"未审点"过了一遍但没扫到这里，所以记 P1，不是敞口。

**改法**（`bsl_log.c` 249 行）：
- `log_irq_save()` / `log_irq_restore()`：`__get_PRIMASK()` → `__disable_irq()` → 退出 `__set_PRIMASK()`。
  用 CMSIS 而**不是** `taskENTER_CRITICAL`：`LAYER_DEPENDENCIES["bsl"]` 只允许 `hal`，bsl 一 include
  内核头就越级（`check` 的 A 块直接判越级）。保存-恢复式还支持嵌套——panic 路径已在关中断状态下进来时，
  退出不会被提前开中断。PRIMASK 同时屏蔽 PendSV，任务切换同样被挡住，对"几十字节的拷贝"够用且是微秒级。
- `bsl_log_puts()`：临界区内只做 `ring_absorb()` + 判 ready + 抢 `s_uart_busy`（ready 要在区内重测，
  因为 `bsl_device_*` 的状态可能刚被别的任务改过）；**临界区外**才 `board_debug_uart_puts()`
  （115200 下约 5 ms，绝不能关中断）。抢不到占用标志就只入 ring 不写串口——ring 里仍有完整副本。
- `bsl_log_dump_ring()`：在 ready 判断之后 `__disable_irq()` **且不恢复**。它只从 `fml_panic()` 调用，
  紧接着就是 `osl_panic_report()` 的关中断自旋，不需要还；同时把整个 dump 期间对 ring 的读锁住，
  倒出来的行不会被别的任务半途改写。

**代价（实测，不是估算）**：`text` 86168 → **86232（+64 B）**，`bss` 21984 → **21992（+8 B：`s_uart_busy` 4 B + 对齐）**；
`bsl_log_puts` = **0x54 = 84 B**，`bsl_log_dump_ring` = **0x60 = 96 B**（user 档被拆成 8 B 外壳 + `bsl_log_puts.part.0` 184 B）。
两档 `build` EXIT=0、**零真告警**（`git grep` 过：`bash.exe: warning: could not find /tmp` 是 cygwin 噪声，统计时排除）。

### 2) 治不好的部分：跨任务整行交错（已知敞口，不是缺陷）

`bsl_log_mod_puts()` 分 4 次调 `bsl_log_puts("[", mod, "] ", s)`，`bsl_log_put_dec()` 按位分多次调。
每次调用现在是原子的，但**一行由多次调用拼成**，中间照样能被另一任务插入，得到
`[led ] [key] button released` 这种混行。根治只有两条路：给 bsl 一个可阻塞的互斥（要引 osl 门面，
破 `LAYER_DEPENDENCIES`），或约定"只有单任务写日志"（把 apl 的日志收口到一个任务，代价是别的任务
失去自己的行前缀）。两条都要动分层或动调用方，本轮不做。**现场见到混行先看这一条**。

### 3) `s_uart_busy` 的死锁面（取舍）

`board_debug_uart_puts()` 若内部死循环后不再返回，标志永不清 → 之后所有日志都不再上屏（ring 仍完整可 dump）。
取的是"宁可不上屏，也不要把两条字符串搅成一条"，且 ring 有副本。显式取舍，记在这里。

## 2026-11-22 第九轮：把"UART 占用卡死"从静默改成可观测

第七轮把 `s_uart_busy` 的死锁面记成"取舍"就收工了。第九轮把它当缺陷处理：取舍的意思是
"知道代价、接受代价"，而这里的代价是**观察能力本身**——日志不上屏（ring 仍有），
现场无法区分"日志确实没打"与"串口一直在丢"，这正是排查最怕的那种静默。

### 1) 机制与改法

**触发**：`board_debug_uart_puts()` 若在 HAL 的等待循环里卡住（等 TC 标志碰上时钟/引脚问题），
或返回到清标志之前被复位/异常打断，`s_uart_busy` 永远是 1 —— 此后每一行日志都只进 ring，
串口一个字都不出。没有计数、没有提示、没有任何旁证。

**改法**（`bsl_log.c` 249 → 323 行）：
- 常量 `BSL_LOG_UART_BUSY_TIMEOUT_MS = 50`：115200 下 60 B 一行约 5.2 ms，50 ms 是十倍余量。
- `s_uart_busy_tick` 记抢到占用的时刻（`HAL_GetTick`，契约是 HAL 的、实现住 `osl_boot.c`，
  所以仍然只算 `bsl → hal` 的允许边）。下一次抢占用时若 `HAL_GetTick() - s_uart_busy_tick >= 50`，
  判定上一次卡住，**强制收回标志**，日志恢复上屏。
- `s_uart_drops` 计数：因占用未清而没上屏的行数。读它进同一把 PRIMASK 临界区。
- banner 尾部若有丢行，追加 `(uart busy: N line(s) not shown)`；
  panic dump 尾部追加 `--- uart busy: N line(s) never reached serial ---`（用独立的
  `dump_uart_dec()` 只往串口吐字符，不经 `bsl_log_puts`，否则会把要倒的历史覆盖回 ring）。

**代价（实测）**：`text` 86232 → **86576（+344 B）**——其中大头是两条文案常量与 `dump_uart_dec`
（0x68 = 104 B），逻辑本身约 90 B；`bsl_log_puts` 84 → **136 B（0x88）**，`bsl_log_dump_ring`
96 → **136 B（0x88）**；`bss` 21992 → **22000（+8 B：`s_uart_busy_tick` + `s_uart_drops`）**。
两档 EXIT=0、零真告警；`check` 七块全绿（`API 面 91 个声明全部在镜像`）。

**可观测性证明**：`nm` 现在能查到 `s_uart_drops`（`0x20000128`）、`s_uart_busy_tick`（`0x2000012c`）、
`dump_uart_dec`（0x68 @ `0x08001df8`）——改动不是"写了注释说会打印"，符号与体积都对得上。

### 2) 订正：`debug/` 存档不该扣 0.4（文档-代码一致）

| **DTS 落点** | 源（`*.dtsi`，由 xlsx 唯一决定）入库在 `project/dts/`；产物（`apollo.dts` / `apollo.dtb`）落 `out/dts/` 且不入库 | 生成器只留一个落点，禁止在 `docs/hardware/pinmap/` 下留副本（第三轮已删） |
| **`fml` 层保留** | 职责 = 故障播报门面（倒环形日志 + 转 osl 码表），54 行是薄门面而非空壳 | 删层会让 apl 直接依赖 bsl_log + osl_panic，见第五轮 2 |
| **vendored 保持 upstream 目录** | `osl/src/freertos/` 不迁 `third_party/`，便于整块升级内核 | 迁移要重做目录扫描与 30 个头 `-I`，收益小于代价 |
| **段跨度 vs 内容边界** | 对拍 DTB 文件大小只用 `bsl_dtb_start/bsl_dtb_end`（内容边界）；`_sdtb/_edtb` 是段跨度，含 `.align 4`(=16 B) 填充 | `board_dtb.s` 注释与 `refcheck` 判据均已按此写 |
| **FDT API 分两族** | `bsl_fdt_init` 族：0 成功 / 负值失败码；`bsl_fdt_prop_*` 族：0 = 缺失或读失败 | 两族语义不同，不强行统一 |
| **HSE 两份声明必须相等** | DTB 的 `clocks.hse-frequency` 是板级记录，编译期 `HSE_VALUE` 是 PLL 计算输入；`board_system_init()` 对拍，不等即码 3 | DTB 值 0 = 未声明，不约束；非 0 必须等于宏（第四轮） |
| **极性取自 DTB 属性值** | `active-low` / `pressed-high` 按第四 cell 的值判（`0` 即 high-active），布尔形态（无值）记为真 | `bsl_fdt_prop_flag` 第三轮修正，不再"有属性即真" |

## 维护规则

1. 新增架构风险：写清**机制**（触发条件、被破坏的语义、为什么静默）与**复现命令 + 期望的失败现象**。
   还没有可复现判据的，记入「已知敞口」，不算关闭。
2. 关闭条目：必须有**改前 / 改后的可观测差异**（EXIT 码、日志行、`nm` 字节数、段地址、哈希幂等、
   必要时上板波形）。门禁已删除（2026-11-22），没有自动化红测可跑，因此"我把代码改对了"不算证明。
3. 修完缺陷要回填代价：代码体积变化、text/RAM 变化、新增的全局状态。别只写"已修复"。
4. 不编造历史编号；对话里的 Nx 无法与仓库行级对应时，只写机制名。

改构建判据或层图时，同步 [.skills/文档维护.md](./文档维护.md) 与 [工程规格.md](./工程规格.md)。
