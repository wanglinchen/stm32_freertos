== 三、应答清单与前一张纸的矛盾（这次测量的目的） ==

`i2c scan` 的结果与 P1 勘探记录**逐字相同**（`1a 1e 20 50 68`），说明两次扫描
是同一条总线、同一套时序 —— P1 记录本身没错，错的是对它的解读。

| 地址 | 应答 | 读寄存器 | 身份（实测 + 数据手册） | 表里原来写的 |
|---|---|---|---|---|
| `0x10` | **无** | — | ES8388 不响应（CE=0 时它应当在 0x10） | ES8388 `board_es8388` |
| `0x1a` | 有 | **NACK** | **WM8978**：7 位地址 0x1A 是它的固定地址；WM8978 的 **I2C 只支持写**，没有读通路 —— 地址阶段 ACK、读方向 NACK 正是这个特性的指纹 | （未列出） |
| `0x1e` | 有 | `0x03` | AP3216C（ALS/接近） | ST480MC `0x0C`（**无应答**） |
| `0x20` | 有 | `0x00` | PCF8574（P0=BEEP / P1=AP_INT / … ） | 与表一致 |
| `0x50` | 有 | `0xff` | 24C02 EEPROM | 与表一致 |
| `0x68` | 有 | `r75=0x71` | **MPU9250**（`WHO_AM_I(0x75)=0x71`） | QMI8658A `0x6A/0x6B`（**无应答**） |

结论（写给 P6c / P6d 的开工条件）：
1. 板上**没有** ES8388。pinmap 里 "ES8388 的 MCLK/SDOUT/LRCK/SCLK/SDIN" 这组
   注释与实际装配件不符（SAI1 的五个脚确实接 codec，但器件是 WM8978）。
2. `0x1A` 的"地址 ACK + 读 NACK"不是坏总线，是 WM8978 只写 I2C 的正常表现。
   所以 P6c 的 codec 驱动要按 **WM8978 的 16 位写事务**（7 位寄存器号 + 9 位数据）
   实现，不能用 `read_reg8` 去"读回校验" —— 这也是为什么本批**只提供 `read_reg8`、
   不提供 `write_reg8`**：写到 codec 上要靠 9 位数据格式，形状不同，P6c 再定。
3. P6d 的 IMU 是 MPU9250（`0x68`），不是 QMI8658A；ALS 是 AP3216C（`0x1E`），
   不是 ST480MC（`0x0C`，无应答）。
4. **待最终确认**：WM8978 的型号是从"地址 + 只写特性 + SAI 引脚"三条推出的，
   还没有让它发出过声音。P6c 第一步（MCLK + I2S 送一段正弦/静音序列）能一锤定音；
   若那时发现不是 WM8978，先改 §1.1 第 14 行再改驱动。


== 四、触摸偶发 FAIL 的根因（本批顺带修掉） ==

现象：13 项里 `touch` 随机 FAIL（`[bsl] device init failed: touch rc=-2`），
此前统计约 1/4 的复位。
诊断：给 `board_touch_init` 的 PID 读加了"读到的 4 字节原样打印"，
一次失败复位直接给出答案：

  [touch] pid raw=0b 00 00 00
  [bsl] device init failed: touch rc=-2

根因：GT9xxx 用 **INT 脚在复位释放那一刻的电平锁存自己的 I2C 地址**
（INT 高 → 0x14，INT 低 → 0x5D）。原代码的顺序是"先释放 RST，再把 INT 配成
浮空输入"，于是释放瞬间 INT 停在复位默认态，锁到的地址不确定 —— 有时锁到 0x14
（读到 9147），有时锁到别的（读到 `0b 00 00 00`）。参考工程是先把 INT 配成上拉、
再动 RST，本工程原先漏了这一条。

修法（`bsl/src/board_touch.c`）：RST 拉低之前先把 INT 当推挽输出拉高 → 10 ms →
释放 RST → 保留 10 ms → **再把 INT 切成浮空输入**（只读电平，不用中断）→ 100 ms
→ 读 PID。另把 PID 重试的判据从"总线没报错"改成"读到了且认得"（上电未就绪时
读回 4 个 0 也是 `BSL_OK`，只看 rc 会把"垃圾内容"和"没有器件"混成一句）。

复测：连续 5 次复位 `touch id=9147 points=0 PASS`，`result 13 pass 13 fail 0`。


== 五、蜂鸣器永久禁用（用户 2026-11-25 指示） ==

要求原文："关闭蜂鸣器，以后都不要打开，记在 skill 中"。

落地方式（断在唯一执行器，不在调用方各自自觉）：
- `bsl/src/board_beep.c` 加 `BEEP_ALLOW_ON 0`：`beep_set_pcf8574_logical(on=1)`
  先被改成 0，再走原逻辑，并**只打一次**
  `[beep] on request ignored: buzzer disabled by policy`。
  PCF8574 的 P0 从此只会被写成"静音"值，任何新调用方都绕不过去。
- `fml_shell` 的 `beep` 命令**删除**（命令表 6 条：help/uptime/rtc/temp/led/i2c），
  敲 `beep 100` 得到 `unknown 'beep', type help`。
- `app_beep` 保留（对照表里它是参考工程 24 个应用之一，删了等于不落地），
  但窗口标题改为 `BEEP - disabled`，日志由 `on` 改成 `req on (muted)` ——
  请求确实到了执行器、声音不发出，日志不说假话。
- `app_sample` 的开机提示音与按键提示音调用保留（它们会撞到同一个断路器），
  所以每次上电都能看到那一行 ignored，作为"断路器在位"的证据。
- 规则写进 `.skills/SKILL.md`「硬规则」第一条：不许改 `BEEP_ALLOW_ON`、不许绕
  执行器写 P0、不许新增会响的命令/应用；需要提示用屏幕或串口。

实测：每次上电日志恰好一行
`[beep] on request ignored: buzzer disabled by policy`，之后无任何响声请求记录。

== 七、未覆盖 / 限制 ==

1. WM8978 型号尚未被声音证实（见第三节第 4 条），P6c 第一步用 MCLK+I2S 定音。
2. `i2c scan` 只发地址、不发数据；能证明"器件在"，不能证明"器件能按预期工作"。
3. 扫描范围 0x08..0x77，不含 10 位地址器件与 I2C 保留地址段。
4. 本批未碰 codec/IMU 的寄存器写路径，也没有建立任何 codec/imu 的 DTB 节点。
5. 触摸修复的验证是 5 次上电复位（都是 MCU 复位、触摸 IC 未断电）；**冷启动**
   （整板断电）未做，缺少一次"整机上电"的样本。
6. 蜂鸣器"不响"只能由人耳确认；串口只能证明"请求被拦下"。
