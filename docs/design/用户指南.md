# 用户指南：构建 → 编译 → 刷机 → 调试

目标板：**正点原子 Apollo V2 / STM32F429IGT6**，调试口 **SWD**，调试串口 **USART1（PA9/PA10，115200 8N1）**。

本文只讲**按顺序该做什么、每步的成功判据、失败先查什么**。装什么工具、为什么这样分层，分别看 [搭建环境.md](./搭建环境.md) 与 [系统设计.md](./系统设计.md)；契约（冲突时以它为准）见 [.skills/工程规格.md](../../.skills/工程规格.md)。

> 证据边界：第 1–3、9 节的命令在本仓库本机实测过（含 EXIT 码与体积读数）；第 4–6 节的刷机/调试命令按 `flash/flash.py`、`debug/capture.py` 的真实参数与既有文档整理，**本机未接板验证**，首次使用请按「成功判据」逐项确认。

## 1 五分钟跑通（Windows）

在仓库根目录（下文记作 `<仓库根>`，本机为 `D:\Users\Local\stm32-freertos`）：

```powershell
cd <仓库根>
python build\build.py install-toolchain     # 首次；已装则只打印版本
python build\build.py set-buildenv --check  # 检查 arm-none-eabi-gcc / make / sh
python build\build.py build                 # 内含 update，编 userdebug + user 两档
```

Linux 把 `python` 换成 `python3`、反斜杠换成 `/`。

**成功判据**（三条都要对）：

1. `update` 段出现 `已生成 out/dts/apollo.dts → …apollo.dtb（N 字节）`，且**没有任何 dtc 诊断**（Warning 也算失败）；
2. 两档各打印 `编译 userdebug（OPT=-Og DEBUG=g3）` / `编译 user（OPT=-Os DEBUG=g0）` 并退出码 0（`-Werror`，一条告警即失败）；
3. `out/<档位>/release/<时间戳>/` 下出现 `stm32-freertos.{elf,hex,bin,map}` 四个文件。

本机实测读数（2026-11-22 最新）：`-Og` userdebug `text=86576`（其中内嵌 `.dtb` 段 63888 B，扣掉后代码 22688 B）、`data=16`、`bss=22000`（RAM 11.20%，Flash 8.26%）；`-Os` user `text=83652`、`data=16`、`bss=21992`（RAM 11.19%，Flash 7.98%）。你的数字应与此同量级，差几百字节属正常（改动不同）。

> 构建期间每条命令都会刷一行 `bash.exe: warning: could not find /tmp, please create!`。这是 cygwin/MSYS 的临时目录提示，**无害**，正式临时目录是 `out/tmp`。

## 2 系统构建（`update`）：真源与生成物

### 2.1 三个真源

| 真源 | 位置 | 改它影响 |
|---|---|---|
| 板级引脚表（DTS 唯一真源） | `docs/hardware/pinmap/stm32f429_default_gpio_pinmap.xlsx`、`apollo_alternate_gpio_pinmap.xlsx` + 同目录 `gen_dts.py` | 引脚复用/命名、按键与 LED 的脚与极性、蜂鸣器、调试串口、时钟频率 |
| 配置（defconfig） | `project/config/stm32f429_defconfig_common`（公共项）、`stm32f429_defconfig_user{debug}`（档位差异层）、各层 `Kconfig` | 编哪些源文件、HAL 模块开关、FreeRTOS 配置 |
| 源码树本身 | 各层 `src/`、`inc/` | 编译单元、头文件可见性、链接顺序 |

### 2.2 `update` 生成什么（勿手改）

```text
python build\build.py update
```

产物（脚本会逐个打印"已生成…"）：

- `project/dts/stm32f429_gpio_default.dtsi`（140 脚平台默认，由 pinmap 脚本产）
- `project/dts/apollo_gpio_overlay.dtsi`（板级覆盖）
- `out/dts/apollo.dts` + `apollo.dtb`（两份 dtsi 合成单树后用 `dtc` 编译）
- `toolchain.make`、各层 `Makefile` / `Kconfig`、`project/config/stm32f429_defconfig_common` + 两档差异层、`out/<档位>/.config`

`apollo.dtb` 由链接脚本排进 `.dtb` 段、随固件一起烧（`bsl/src/board_dtb.s` 的 `.incbin`），
运行期由 `bsl_fdt` 解析、`bsl/src/board_rt.c` 分发到各驱动。**C 里不再有生成的引脚头**：
`bsl/inc/board_device_registry.h` 与 `osl/inc/board_panic_hw.h` 已改为手写常量（后者是 panic
专用，不允许运行期遍历 FDT）。

### 2.3 改什么必须 update

| 你改了什么 | 要不要 `update` |
|---|---|
| 只改 `*.c` / `*.h` 函数体或局部变量 | 不用，`build --fast` 即可增量编译 |
| 新增 / 删除源文件、改 `Kconfig`、改 defconfig | **必须**（否则 Makefile 里没有这个单元，链接缺符号） |
| 改 `docs/hardware/pinmap/*.xlsx`（引脚/极性/复用） | **必须**（dts 与 `apollo.dtb` 都要重生成，否则固件还是旧引脚） |
| 改 `docs/hardware/pinmap/gen_dts.py`、`project/generate.py`、`build/build.py` | **必须**（生成链本身变了） |
| 改 `bsl/inc/board_device_registry.h` / `osl/inc/board_panic_hw.h` | 不用 update（手写文件），但要审核改动是否与 DTS 一致 |

### 2.4 生成链的自检口径

`update` 自身就是自检：`gen_dts.py` 读两个 xlsx 出 dtsi → 合成 `apollo.dts` → `dtc` 编译。
**任何 dtc 诊断（含 Warning）都判失败**，退出码非 0；成功时打印
`已生成 out/dts/apollo.dts → …apollo.dtb（N 字节）`。
（此前有 `python project\generate.py check` 的 10 项 EDT 自检，随 EDT/bindings 链一起删除。）

## 3 编译（`build`）

### 3.1 两个档位

| 档位 | 优化/调试 | 用途 | elf 默认位置 |
|---|---|---|---|
| `userdebug` | `-Og -g3` | 调试、`capture.py`、**刷机默认档** | `out\userdebug\objects\target\` |
| `user` | `-Os -g0` | 发布 / 量产，用 `hex` | `out\user\objects\target\` |

`build` 默认两档都编，并各拷 4 个文件到 `out/<档位>/release/<时间戳>/`。

```powershell
python build\build.py build --variant userdebug   # 只编一档
python build\build.py build --fast                # 跳过 update（仅改了 .c/.h 时用）
```

### 3.2 告警即错误

`CFLAGS` 固定含 `-Wall -Wextra -Werror -Wmissing-prototypes -Wstrict-prototypes`（C++ 侧不加后两个）。实测基线零告警，所以：

- 编出**任何** warning 就等于失败，先把它当错误读；
- `-Wmissing-prototypes` 报的是「定义了函数但没在头里声明」——正确做法是把声明补进对应层 `inc/*.h`，不是加 `#pragma`；
- 确实无法避免时，先在该提交里写明原因，再考虑局部 `#pragma GCC diagnostic`，不要整体降级警告级别。

### 3.3 常见编译失败

| 报错形态 | 多半原因 | 处理 |
|---|---|---|
| `fatal error: xxx.h: No such file or directory` | 跨层直接 include 了别层的 `inc` | 层边只允许「向下」依赖；改用本层头 + 依赖注入，见 [系统设计.md](./系统设计.md) 第二部分 |
| `undefined reference to 'board_xxx'` | 新文件没被 `update` 收进 Makefile，或符号被 `--gc-sections` 丢弃 | 先 `update`；仍缺就查该层 `Makefile` 的 `LOCAL_OBJS` 与 `nm` 符号 |
| `too many initializers` | 数组长度取了生成值、初始化器条数手写 | 改由生成器产出的宏（如 `BOARD_DTS_KEY_HW_INITIALIZERS`），别手写逐项 |
| `-Wmissing-prototypes: no previous prototype` | 头文件没声明，或源文件没 include 自己的头 | 补声明；`system_*.c` 这类要 include 自己的头 |
| `Error 49`（每个被重编文件都报） | MSYS `sh` 里的 `python3` 是失效别名 | 已由 `toolchain.make` 按 `OS` 选 `python` / `python3` 兜住；若复现，检查该文件是否被手改 |

## 4 刷机

### 4.1 一次性准备

```powershell
python flash\flash.py install-openocd          # 装到 tool\win_x86_64\bin\openocd.exe
python flash\flash.py install-stlink-driver    # Windows 装 WinUSB（需管理员）
python flash\flash.py set-buildenv --check     # 检查工具链 + OpenOCD + make/sh
```

Linux 还要 udev 规则（`tool/linux_x86_64/openocd/contrib/60-openocd.rules`），WSL 另需 usbipd，详见 [搭建环境.md](./搭建环境.md#wsl-刷机与-windows-共用仓库)。

### 4.2 刷

```powershell
python flash\flash.py                              # 默认刷 userdebug 的 elf
python flash\flash.py flash out\user\objects\target\stm32-freertos.elf   # 指定 elf
python flash\flash.py flash --interface interface/stlink-v2-1.cfg        # 接线是 v2-1 时
```

底层等价于：

```text
openocd -s tool\win_x86_64\openocd\scripts -f interface/stlink.cfg -f target/stm32f4x.cfg `
        -c "program <elf> verify reset exit"
```

**成功判据**：OpenOCD 打印 `Verified OK` 后进程退出；板子自动复位。

量产用 `hex`（不带 `reset`）：

```text
-c "program stm32-freertos.hex verify exit"
```

### 4.3 失败矩阵

| 现象 | 先查 | 处理 |
|---|---|---|
| `Error: libusb_init() failed` | ST-Link 驱动 / USB 线 | `install-stlink-driver`，换口换线 |
| `Error: open failed` | 目标没上电、SWD 线序 | 上电；确认 SWDIO/SWCLK/GND 三线 |
| `Can't find target/stm32f4x.cfg` | 少了 `-s` 脚本目录 | 加 `-s tool\<平台>\openocd\scripts` |
| 认到 ST-Link 但认不到芯片 | BOOT0、供电、芯片型号 | BOOT0 从 Flash 启动；确认是 F429IGT6 |
| 烧完不跑 | 少了 `reset` | 用 `program … verify reset exit`，或手动复位 |
| `dpinst` 返回 0x3 | `tool\win_x86_64` 目录区分大小写 | `fsutil file facility queryCaseSensitiveInfo` 关掉，或重跑 `install-stlink-driver` |

## 5 上板第一次验证（不用调试器也能确认"活着"）

三条独立判据，**全中**才算启动成功：

| 判据 | 期望 |
|---|---|
| 串口（115200 8N1） | 一行 `stm32-freertos: USART1 115200 debug ready` |
| LED | 红/绿**每秒交替**一次，蓝常灭（`SAMPLE_LED_PERIOD_MS = 1000`） |
| 按键 | 按住任一键 → 蜂鸣器响；松开 → 停响；串口打印 `[btn] stable=1 raw WKU=… K0=… K1=… K2=…`（10 ms 轮询、3 次去抖） |

`raw WKU/K0/K1/K2` 是**引脚原始电平**（1 = 高）。板载按键 WK_UP 高有效，KEY0/1/2 低有效，所以松开时典型是 `WKU=0 K0=1 K1=1 K2=1`——这一行能直接证明 DTS 里的按键极性没有反。

串口出现字符但乱码 → 波特率不是 115200；完全没有输出 → 先看 §6.4 的灯闪次数。

## 6 调试

### 6.1 串口日志

- 物理口：板载 USB 转串口（CH340）→ USART1，**115200 8N1**，无需流控。
- 代码路径：`BSL_LOG_INF(...)` → `bsl_log_puts()` → `board_debug_uart_puts()` → USART1。
- 级别：编译期宏 `BSL_LOG_LEVEL`，默认 `BSL_LOG_LEVEL_INF`（`bsl/inc/bsl_log.h:10`）。`VARIANT_LAYER_LOG_DEFCONFIG` 里的分档阈值**尚未接线**（Kconfig 无对应符号、Makefile 也没有 `-D` 注入），所以两档目前都是 INF；**不要**在 `.c` 里临时改宏。

### 6.2 GDB（OpenOCD 作 GDB Server）

终端 1（前台占用，别关）：

```powershell
python flash\flash.py debug-server
```

终端 2：

```text
tool\win_x86_64\bin\arm-none-eabi-gdb.exe out\userdebug\objects\target\stm32-freertos.elf
(gdb) target extended-remote :3333
(gdb) monitor reset halt
(gdb) load
(gdb) monitor reset run
```

GDB 默认端口 3333，telnet 4444。pyOCD / J-Link / CubeProgrammer 作 Server 也可，见 [搭建环境.md](./搭建环境.md#连接示例openocd--本仓库-gdb)。

### 6.3 现场快照 `capture.py`

不想开 GDB 交互、只想把现场落成文件时：

```powershell
python build\build.py build                                    # 符号地址从产物解析
python debug\capture.py red-led-constant                       # 生成 debug/<问题>_<时间>/snapshot.md
```

| 参数 | 含义 |
|---|---|
| `--elf PATH` | 默认 `out/userdebug/objects/target/stm32-freertos.elf` |
| `--sample-gpio N` | 采样 `GPIOB->ODR` 间隔毫秒（默认 1000；0 = 不采样） |
| `--no-halt` | 只连不 `halt`（读值可能抖动） |

`snapshot.md` 会写入 PC/LR 与 `addr2line` 符号、`g_boot_stage`、`g_clock_fail_sub`、`g_panic_record`、SysTick、`RCC`/`PWR`/`GPIOB`、`GPIOB->ODR` 采样。目录规范见 [debug/README.md](../../debug/README.md)。

### 6.4 panic 现场（最容易踩坏的一步）

板子已经跑飞时，**不要**先 `load` / `program`——那会擦掉 RAM 里 `.noinit` 段的现场。

正确顺序：`monitor reset halt`（复位但**不擦** RAM 内容；若断电则现场已丢）→ 直接读变量：

```text
(gdb) p g_panic_record        # .noinit，31 个字段
(gdb) p g_boot_stage          # 码 4 时分辨是 HAL_Init 还是 SystemClock_Config
```

**先看灯，再开调试器**：panic 的播报方式是唯一一种——三灯按二进制逐位闪，**4 轮**，然后全亮、关中断自旋。数出闪的次数即故障码：

| 码 | 含义 | 备注 |
|---|---|---|
| 1 | `vTaskStartScheduler()` 返回 | 调度器没起来，堆不足 |
| 2 | `xTaskCreate` 失败 / `vApplicationMallocFailedHook` | FreeRTOS 堆不足，或原 malloc 失败 |
| 3 | `configASSERT` / HAL `assert_failed` | 文件名 + 行号进 record |
| 4 | `board_system_init()` 返回非 0 | `g_boot_stage` = 1 → `HAL_Init` 失败；= 2 → `SystemClock_Config` 失败（HSE/PLL）；= 3 → DTB 的 `hse-frequency` 与 `stm32f4xx_hal_conf.h` 的 `HSE_VALUE` 不一致。三者排查方向互斥 |
| 5 | newlib `_sbrk` 越界 | 是 newlib 堆，不是 FreeRTOS 堆 |
| 6 | HardFault / MemManage / BusFault / UsageFault / `UnhandledIRQ_Handler` | 细分读 `fault_kind` / `unhandled_irq` |
| 7 | `vApplicationStackOverflowHook`（带任务名）/ MSP 守卫（`task` 为 NULL） | 两来源共用码 7 |

码表唯一事实源是 `osl/inc/osl_panic.h` 的 `osl_panic_code_t`，完整字段见 [系统设计.md](./系统设计.md) 第 6 节。

## 8 排障速查

| 现象 | 先做这一步 |
|---|---|
| 完全没输出、灯也不闪 | 供电 / BOOT0；`monitor reset halt` 看 PC 是否在 `0x0800xxxx` |
| 三灯有规律闪 N 次然后全亮 | 数 N → §6.4 码表；断电会丢现场，读 `g_panic_record` 要趁热 |
| 串口有乱码 | 波特率不是 115200，或 TX/RX 接反（PA9=TX） |
| 红灯常亮不交替 | LED 任务没起来（码 2）或 LED 设备注册缺失 |
| 按按键没反应 | 串口看 `[btn] raw …`：电平不随按键变化 → 引脚/极性错误；变化但不响 → 蜂鸣器（PCF8574 走 I2C） |
| 一改就编不过 | 先 `python build\build.py update`；仍报错看 §3.3 |
| `update` 报 dtc 诊断 | dts 结构不合规（重复 unit address、simple-bus 下无 reg 节点等）；按报错行改 `project/generate.py` 的 `_BOARD_NODES` 或 pinmap 脚本 |

## 9 提交前必做

```powershell
python build\build.py update      # 刷新 Makefile/Kconfig，跑 pinmap 脚本产 dts，dtc 编 dtb（零诊断）
python build\build.py build       # 两档都要过，-Werror 零告警
```

要点：

- `update` 的输出必须见到 `apollo.dtb（N 字节）`，且**没有任何 dtc 诊断**；有 Warning 就是失败。
- 门禁（`verify` / `gate-selftest` / `build/checks/`）已于 2026-11-22 整体删除，待重新构建；不要再去跑这两条命令。
- 只改文档或判据时，elf 的 SHA256 应与上次一致；C 源码变了则必然变，属正常。

## 10 常见坑

| 坑 | 说明 |
|---|---|
| `bash.exe: warning: could not find /tmp` | cygwin/MSYS 缺 `/tmp`，无害；正式临时目录是 `out/tmp` |
| PowerShell 前台超过约 15 s 被转后台 | 构建/`update` 这类长命令用后台任务并取回输出，别以为"卡死" |
| `python3` 在 Windows 不存在 | 用 `python`；`toolchain.make` 已按 `OS` 自动二选一 |
| 手改 `project/dts/*` | 下次 `update` 覆盖；要改引脚就改 `docs/hardware/pinmap/*.xlsx` 或 `generate.py` |
| 用 `build --fast` 改过生成物相关输入 | Makefile 与 `.config` 不会更新，会缺符号或带错宏 |
| 刷机前忘了 build | `flash.py` 刷的是 `objects/target` 里的**现有** elf，可能是上一次的 |
| panic 后先烧固件 | 会把 `.noinit` 现场擦掉，再也读不到 |
