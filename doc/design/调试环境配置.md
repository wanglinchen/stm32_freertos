# 调试环境配置

本文只描述**本仓库已经具备的调试能力**，以及拿到 `g_panic_record` / 硬件异常现场的具体步骤。
工具链安装见 [开发环境配置.md](./开发环境配置.md)。

## 本仓库提供什么

| 项 | 位置 / 事实 |
|----|-------------|
| GDB 客户端 | `tool/win_x86_64/bin/arm-none-eabi-gdb.exe`（随 `build/install-toolchain.py` 安装，GCC 13.3.1） |
| 符号核查工具 | 同目录的 `arm-none-eabi-nm.exe` / `arm-none-eabi-objdump.exe` / `arm-none-eabi-size.exe` |
| 带调试信息的产物 | `out/target/stm32-freertos.elf`（`-Og -g3`，未 strip；当前约 1.34 MB） |
| 故障记录区 | `g_panic_record`（`volatile`，见 `osl/src/freertos_port_st.c`） |
| 最近一次 `printf` | `g_last_write[64]`（本工程没有串口，`_write` 只落在内存里） |
| 提示灯 | PH10 / PH11 / PH12，共阳低电平点亮 |

## 本仓库不提供什么

仓库内**没有** OpenOCD、pyOCD、J-Link / ST-Link 的 GDB server，也没有 `.svd`、`.launch`、调试脚本。
也就是说：GDB 客户端已经有了，但"谁把 SWD 上的数据转成 GDB remote 协议"需要本机另外装一个。
三种常见选择（任选其一，均**不在**本仓库内分发，安装方式以各自官网为准）：

- ST-Link：`st-util` / STM32CubeProgrammer 的 GDB server
- CMSIS-DAP：`pyocd gdbserver`
- J-Link：`JLinkGDBServer`

它们默认监听 `:3333`，下面的连接命令都按这个端口写。

## 连接与加载

```text
# 另开一个终端先起 GDB server（示例：pyOCD）
pyocd gdbserver --target stm32f429xitx

# 再连 GDB
tool\win_x86_64\bin\arm-none-eabi-gdb.exe out\target\stm32-freertos.elf
(gdb) target extended-remote :3333
(gdb) monitor reset halt
(gdb) load
(gdb) break main
(gdb) continue
```

只读内存、不改板子（比如板子已经停在故障点）时，**不要**执行 `load`，直接
`target extended-remote :3333` 后 `info registers` / `p g_panic_record` 即可。

## 读故障现场（核心）

### 一条命令看全部

```text
(gdb) p g_panic_record
```

`code` 与三灯对应（见文末表格）；硬件异常时 `fault_kind` 说明是哪一类，`fault_pc`
指向出错指令，`fault_cfsr` / `fault_hfsr` 说明原因。

### 字段含义

| 字段 | 含义 |
|------|------|
| `magic` | `0x50414E43`（`"PANC"`）；为 0 说明从未进入 panic 路径 |
| `code` | 1 栈溢出 / 2 堆或任务创建失败 / 3 `configASSERT` / 5 newlib 堆耗尽 / 6 硬件异常 |
| `task` / `task_name` | 出事的任务句柄与名字（栈溢出钩子填写） |
| `assert_file` / `assert_line` | `configASSERT` 失败位置（指针 + 行号） |
| `fault_kind` | 1 HardFault / 2 MemManage / 3 BusFault / 4 UsageFault |
| `fault_cfsr` / `fault_hfsr` | 可配置故障状态 / 硬故障状态寄存器快照 |
| `fault_mmfar` / `fault_bfar` | 触发 MemManage / BusFault 的地址（对应 CFSR 的 MMARVALID / BFARVALID） |
| `fault_exc_return` | 异常进入时的 `EXC_RETURN`（bit2 决定异常帧在 MSP 还是 PSP） |
| `fault_sp` | 取帧时用的栈指针 |
| `fault_r0` … `fault_xpsr` | 异常帧里的 8 个寄存器：`%r0` `%r1` `%r2` `%r3` `%r12` `%lr` `%pc` `%xpsr` |

### 读到的 pc 怎么用

```text
(gdb) info symbol g_panic_record.fault_pc
(gdb) list *g_panic_record.fault_pc
(gdb) x/4i g_panic_record.fault_pc
```

`fault_pc` 是**出错的那条指令**，不是 `fault_report` 里的地址——后者才是 handler 自己。
如果 `fault_kind` 是 1 而 `fault_hfsr` 的 `FORCED` 位（bit30）为 1，说明是从
MemManage/BusFault/UsageFault 升级上来的，真实原因仍在 `fault_cfsr` 里。

## 硬件异常的排查顺序

1. **先看 `fault_cfsr` 的分组**（bit0-7 MemManage、bit8-15 BusFault、bit16-31 UsageFault）：
   常见的 `PRECISERR`（精确总线错误，地址在 `fault_bfar`）、`IBUSERR`（取指失败）、
   `UNALIGNED`（非对齐访问）、`DIVBYZERO`（除零）、`INVSTATE`（`%xpsr.T` 被清成 0，
   典型是跳到了错误的函数指针）。
2. **再看 `fault_pc` / `fault_lr`**：`%pc` 定位出错指令，`%lr` 说明是从哪次调用进去的
   （`bl` 之后的地址，减 4 或减 2 就是调用点）。
3. **最后看 `fault_sp` 是否落在栈里**：`0x20000000..0x20030000` 之外说明栈指针本身已经废了，
   这时异常帧字段会是 0（`fault_report` 有意跳过取帧）。
4. 栈溢出优先怀疑：阈值与钩子见 `.skills/工程规格.md`「故障可观测」；任务栈在 FreeRTOS heap
   （32 KB）里，`pvPortMalloc` 失败走 `code 2`。

## 三灯故障码

三灯按二进制位闪 `code`（PH10 = bit0，PH11 = bit1，PH12 = bit2），播报 4 轮后全亮收尾，
然后关中断自旋。因为只有 3 位，"硬件异常"统一用 `6`，细分看 `fault_kind`。

| code | 含义 |
|------|------|
| 1 | 任务栈溢出 |
| 2 | 堆 / 任务创建失败 |
| 3 | `configASSERT` 失败 |
| 4 | `SystemClock_Config` 失败 |
| 5 | newlib 堆耗尽（`_sbrk` 越界） |
| 6 | 硬件异常（HardFault / MemManage / BusFault / UsageFault） |

## 不开 GDB 也能核查

```text
# 四个异常入口是否为强符号，与 Default_Handler 是否同址（同址 = 仍是 Infinite_Loop）
tool\win_x86_64\bin\arm-none-eabi-nm.exe out\target\stm32-freertos.elf | findstr /i "Handler"

# 向量表 0x08000000 起前 8 个字：第 4/5/6/7 个字应指向上面的入口地址（末位 +1 是 Thumb 位）
tool\win_x86_64\bin\arm-none-eabi-objdump.exe -s -j .isr_vector out\target\stm32-freertos.elf

# 时基（DWT）与堆边界符号
tool\win_x86_64\bin\arm-none-eabi-nm.exe out\target\stm32-freertos.elf | findstr /i "sbrk heap"
```

`verify` 会自动断言四个入口是 `T` 且不与 `Default_Handler` 同址；手工核查只在怀疑
"产物与源码不一致"时用。
